## 一句话项目介绍

在 Unity 活动系统中设计并落地曝光、参与、充值三阶段埋点，统一活动归因、每日去重和支付成功补报，为运营分析活动漏斗与收入来源提供可靠数据基础。

## 简历写法

### 精简版

- 负责 Unity 活动曝光、参与、充值埋点体系建设，统一角色、区服、渠道、活动周期与订单归因，覆盖 100+ 活动业务文件。
- 设计曝光/参与每日去重、并发防重及充值订单持久化补报机制，以服务器发货作为充值成功依据，降低重复统计和点击充值误报风险。
- 梳理 Luban 活动配置、`EPromotion` 与业务 Service 的映射关系，识别配置与枚举同步缺口并沉淀活动接入检查流程。

### 技术版

- 基于 Unity C# 和项目 Feature 架构实现 `ActivityTrackManager`，封装三类 Web API、上下文校验、服务端时间去重和异常隔离，业务层通过 `Promotion` 完成统一归因。
- 重构活动充值调用链：下单成功登记游戏订单及活动上下文，服务器发货后确认上报，失败记录持久化并在登录时重试，避免取消支付被计入活动收入。
- 对统一活动容器、独立窗口和历史遗留活动采用自动映射与显式上下文并存策略，解决多活动共用窗口时的错误归因问题。

不要在没有 BI 或线上数据证明时写“提升转化率 X%”或“数据准确率达到 99.9%”。

## STAR 讲述

### S：背景

活动系统有大量不同形态的活动。运营需要分析玩家看到活动后是否参与、参与后是否充值，但原有代码入口分散，充值按钮点击也不能代表真实支付成功，因此缺少统一且可信的漏斗数据。

### T：任务

我需要在不影响活动主流程的前提下，为现有活动体系增加曝光、参与和充值埋点，并解决活动归因、重复统计、支付异步、失败补报和历史活动兼容问题。

### A：行动

我先抽象了统一的 `ActivityTrackContext`，用活动 ID、运营类型和活动周期描述归因上下文；然后实现 `ActivityTrackManager` 和 WebService DTO/路由。

曝光层面，我区分统一活动容器、唯一窗口映射和多活动共用窗口：能唯一判断的自动上报，不能唯一判断的要求业务显式传入实际活动，避免猜错。

参与层面，我把埋点放在服务器业务成功响应之后，而不是按钮点击处，并在大量活动 Service 的成功路径接入。管理器使用角色、区服、活动、事件类型和日期做每日去重，同时用内存集合处理并发防重。

充值层面，我没有在点击充值时上报，而是在游戏服创建订单后保存活动上下文，等服务器发货消息到达再确认充值埋点。上报失败的已支付订单保存在本地，登录后继续补报。

最后我核对了活动 Excel、Luban 配置、`EPromotion` 和 Service 映射，发现配置表与客户端枚举存在同步差异，并整理了后续接入和测试清单。

### R：结果

最终建立了可复用的曝光→参与→充值事件模型，为后端按角色、区服、渠道、活动和订单分析漏斗与收入归因提供了数据基础；同时通过每日去重、真实发货确认和失败补报，提高了数据可靠性，并且统计接口失败不会阻塞玩家业务流程。

## 三分钟回答

“这次任务是给游戏内活动补一套完整的曝光、参与和充值埋点。难点主要有三个：活动形态很多、同一个窗口可能承载不同活动；参与不能只看点击，要以业务成功为准；充值是异步链路，点击购买不等于支付成功。

我的方案是做一个统一的 ActivityTrackManager。业务层传 Promotion 或一个轻量的 ActivityTrackContext，里面包含活动 ID、是否运营活动和本期起止时间。管理器统一补齐角色、区服、渠道，再调用三个后端接口。

曝光方面，我在界面真正显示后上报。窗口能唯一对应活动时自动映射；多个活动共用窗口时不猜 ID，而是由业务传当前 Promotion。参与方面，我把调用接在服务器响应成功和本地状态更新之后，并按角色、区服、活动和日期每日去重。

充值方面采用两阶段确认：活动内创建订单后先保存订单号和活动上下文，收到服务器发货消息才算充值成功并上报。如果埋点请求失败，就持久化保留，重新登录后补报。这样避免了取消支付误报，也避免弱网导致已支付数据直接丢失。

最后我还核对了 Excel 活动控制表、Luban 配置和客户端枚举，发现存在部分活动 ID 不同步的问题。这个任务最终提供的是可靠的活动漏斗和收入归因基础；具体转化率提升需要上线后的 BI 数据验证，我不会在没有数据时夸大。”

## 高频追问

### 为什么参与埋点不放在按钮点击处？

按钮点击只代表意图。网络失败、资源不足或服务器校验不通过时，玩家并没有真正参与。放在业务成功响应后，语义更准确。

### 为什么充值不能在下单时上报？

下单后玩家可能取消、SDK 支付失败或服务器未发货。以服务器发货消息为准，才能接近“真实到账”的业务定义。

### 为什么需要保存 ActivityTrackContext？

支付回调晚于 UI 生命周期。活动窗口可能已经关闭，`Promotion` 对象也不适合持久化。保存纯字段可以跨页面甚至跨登录恢复归因。

### 如何防止重复曝光和参与？

使用服务器日期，并以事件类型、角色、区服、活动 ID 组合缓存；请求进行中再用 HashSet 防并发。只有后端明确新增成功才写每日缓存。

### 为什么充值不按天去重？

同一活动同一天可能存在多笔真实订单，按天去重会丢收入。充值应按游戏订单号幂等。

### `promotion_id` 从哪里来？

来自活动主配置 `HD活动控制表.xlsx` 的 `idx`，运行时通过 `Residentactivities` 和 `Promotion.Id` 使用。它表示活动主类型，不一定代表每一期动态活动实例。

### `is_operate` 怎么判断？

当前客户端根据 `Promotion.EType` 是否属于 `OPERATOR`、`CHARGE_TOTAL`、`CHARGE_RANK` 推导。Excel 也存在 `is_operate` 列，因此需要确保两者一致，长期最好收敛为一个事实来源。

### 最大的技术风险是什么？

当前到账确认按商品 ID 找第一个待支付订单。同一商品短时间出现多笔订单时可能错配。理想方案是支付/发货消息透传游戏订单号并按订单确认。

### 为什么使用 fire-and-forget？

埋点是旁路能力，不能因为统计接口异常阻塞领取奖励或支付发货。管理器内部捕获异常、记录日志，并对充值做持久化补报。

### 你如何证明它有效？

工程上可以通过请求日志、去重测试、取消支付测试、发货成功测试和登录补报测试验证链路正确。业务上是否改善转化需要后端入库与 BI 漏斗数据，不能只凭客户端代码证明。

### 如果重新设计，你会怎么改？

优先让支付成功消息携带订单号；增加待处理订单过期和重试策略；统一 `is_operate` 来源；自动校验 Excel、枚举、Service 和埋点覆盖；把参与行为进一步事件化，减少大量手工调用点。

## 不要夸大的内容

- 不要把“100+ 文件有调用”说成“100+ 独立活动全部完整覆盖”，因为一个活动可能有多个文件或多个触发点。
- 不要说埋点绝对不丢失；本地补报提高可靠性，但仍受卸载、清缓存、协议设计等影响。
- 不要说客户端保证充值全局幂等；真正幂等应由后端按订单号保证。
- 不要把表内所有 ID 都说成已实现；Excel、枚举和业务代码存在同步边界。
- 不要编造转化率、收入或准确率数字。
