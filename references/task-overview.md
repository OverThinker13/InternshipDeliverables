## 任务背景

项目需要统计活动从“被玩家看到”到“实际参与”再到“活动内充值”的完整转化路径。旧代码中活动类型多、入口分散，既有统一活动容器，也有独立窗口和历史遗留活动；充值还跨越下单、SDK 支付、服务器发货等异步阶段，直接在按钮点击时上报会产生误报。

本任务的核心不是简单增加三个 HTTP 请求，而是给大量异构活动建立统一归因模型，并处理重复上报、支付异步、异常重试和特殊活动兼容。

## 需求目标

建立三类活动埋点：

- 曝光：玩家真正打开并看到活动页面。
- 参与：玩家完成该活动定义的有效行为，且业务请求成功。
- 充值：玩家从具体活动发起真实充值，并在支付发货成功后上报。

上报需要携带玩家、区服、渠道、活动 ID、活动类型和活动时间范围；充值还需要游戏订单号，从而支持后端构建活动漏斗和收入归因。

## 最终方案

新增统一的 `ActivityTrackManager`，集中承担：

- 构造活动上下文。
- 曝光、参与、充值请求。
- 每日去重和并发防重。
- 待确认充值订单的本地持久化。
- 登录后补报已经支付但尚未成功上报的订单。
- 请求结果日志和参数校验。

WebService 层增加统一 DTO 和三个接口映射：

- `ActivityTrack/reportExposure`
- `ActivityTrack/reportParticipation`
- `ActivityTrack/reportRecharge`

业务层只负责在“真正发生业务成功”的位置调用管理器，不重复拼装 HTTP 参数。

## 三类埋点

### 曝光

普通活动在 UI 展示后上报。系统通过 `PromotionViewAttribute` 建立窗口类型与活动 ID 的关系；一个窗口只对应一个活动时可自动归因。统一活动容器 `ResidentActivities` 在实际展示对应页签后，用当前 `Promotion` 上报。

周卡、超值首充等独立或遗留窗口无法完全依赖统一映射，因此显式创建 `ActivityTrackContext` 上报。

如果一个窗口类型对应多个活动 ID，管理器不会仅凭窗口类型猜测活动，避免把曝光归到错误活动；这类情况应由业务层传入实际 `Promotion`。

### 参与

参与不是“点击按钮”，而是业务动作成功。调用通常放在请求返回成功、模块数据更新完成的位置，例如领取奖励、抽奖、购买活动商品或完成活动操作之后。

这样可以避免网络失败、条件不足、服务器拒绝时仍被统计为参与。当前工作区可检索到 `ReportParticipation` 分布在 100 多个活动相关文件中；检索行数包含管理器定义和部分多触发活动，不能直接等同于独立活动数量。

### 充值

充值链路采用“两阶段确认”：

1. 活动业务调用带 `Promotion` 或 `ActivityTrackContext` 的 `RechargeOrder` 重载。
2. 游戏服创建订单成功后，记录 `game_order_id + product_id + activity context`，但不立即上报充值成功。
3. SDK 支付及服务器发货完成，客户端收到 `RechargeRewardMessage`。
4. 使用商品 ID 找到待确认订单，标记已支付并调用充值埋点。
5. 后端返回成功后删除本地待处理记录；失败则保留，登录时再次补报。

这样把“活动中发起充值”和“真实到账”关联起来，避免把取消支付、支付失败统计成活动收入。

## 数据字段

通用字段：

- `role_id`：角色 ID。
- `server_id`：区服 ID。
- `channel_id`：子渠道 ID。
- `promotion_id`：活动主 ID。
- `is_operate`：是否运营类活动，值为 0 或 1。
- `activity_start_time`：活动开始 Unix 秒。
- `activity_end_time`：活动结束 Unix 秒。

充值增加：

- `game_order_id`：游戏服订单号，用于幂等和收入归因。

运行时活动时间来自 `Promotion.Duty`；毫秒转换为 Unix 秒。无有效时间或永久活动使用 0。

## 配置关系

主配置文件：`E:/JinHua/xlsx/Datas/HD活动/HD活动控制表.xlsx`。

`xlsx/Datas/table.xml` 将它声明为 `residentactivities`，客户端通过 `ConfigManager.DB.Residentactivities` 读取。关键关系：

- Excel `idx` → `Promotion.Id` / 上报 `promotion_id`。
- Excel `type` → `Promotion.EType`。
- Excel `enum_value` → 手工同步区段 `EPromotion.cs` 的来源。
- Excel 还存在 `is_operate` 列，但当前 `ActivityTrackContext.FromPromotion` 实际通过活动类型判断运营活动：`OPERATOR`、`CHARGE_TOTAL`、`CHARGE_RANK`。这两套定义需要保持一致，否则前后端理解可能偏差。

活动表描述的是活动主类型，不代表每一期动态运营实例都会新增一个 ID。相同 `promotion_id` 可以对应不同批次，具体批次通过活动起止时间区分。

## 覆盖范围

此埋点覆盖的是接入 `Promotion / Residentactivities` 体系并完成客户端业务接点的活动，不等同于后端所有活动、所有外链活动或所有动态活动实例。

审计时表内共有 177 个活动 ID，而 `EPromotion.cs` 有 168 个，Excel 中存在但枚举未同步的 ID 为：

`131、132、706、807、808、809、810、811、812`

这说明 Excel、生成配置、手写枚举和实际客户端实现存在同步边界。新增活动时不能只加 Excel，还要确认：

- `EPromotion` 是否存在。
- 是否有对应 `PromotionAttribute` 和 Service。
- UI 是否能确定实际活动。
- 参与点是否接在业务成功后。
- 活动内现金购买是否把上下文传入充值链路。

## 工程效果

可以确认的工程效果：

- 建立了曝光 → 参与 → 充值的统一事件模型。
- 将分散活动统一归因到角色、区服、渠道、活动主 ID 和活动周期。
- 曝光和参与按角色、区服、活动、事件类型、日期去重。
- 使用内存集合避免同一事件并发重复请求。
- 充值以服务器发货消息为成功依据，降低点击即统计造成的误报。
- 待充值埋点持久化并支持登录补报，提高弱网和接口失败场景的完整性。
- 特殊活动保留显式上下文入口，兼容历史架构。

尚不能直接声称的业务效果：

- 转化率提升了多少。
- 收入提升了多少。
- 数据丢失率下降了多少。

这些需要上线前后监控、后端日志或 BI 数据证明。简历和面试中应说“提供了可分析、可归因的数据基础”，不要虚构百分比。

## 当前边界

- `ConfirmRecharge` 当前按 `productId` 找到第一个未支付记录；同一商品并发产生多个订单时存在错配风险，更稳妥的方案是支付回调携带并按订单号匹配。
- 待处理充值记录没有明确过期清理策略，长期失败记录可能持续保留。
- 多活动共用同一窗口时不能自动判断真实活动，必须显式上报。
- 参与点分散在大量业务文件中，新增活动容易漏接；后续可考虑用统一业务事件或接口约束降低人工维护成本。
- `is_operate` 的 Excel 字段与客户端按 `EType` 推导并存，需要明确唯一事实来源。
- Excel 和 `EPromotion.cs` 存在 9 个 ID 的同步差异。
- 当前工作区对每日缓存 Key 增加了 `RoleId`，避免同账号/设备切角色后互相覆盖；日志分类也调整为 `LOG.WebService`。提交前仍需确认这些本地修改是否已纳入目标版本。

## 重新学习路线

建议按以下顺序重新熟悉：

1. 看 `Core/WebService/ActivityTrack.cs`，记住请求字段和三类事件。
2. 看 `Core/WebService/Manager.cs` 的 `ReportActivityTrack`，理解接口路由和加密请求。
3. 通读 `Features/Activities/ActivityTrackManager.cs`，重点理解上下文、去重、持久化、补报。
4. 看 `ResidentActivities.cs`、周卡和首充，理解自动曝光与特殊曝光。
5. 任选 3 个活动 Service，确认参与上报为什么放在业务成功之后。
6. 看 `Recharge.cs`，手动画出下单、支付、发货、上报时序。
7. 对照 `HD活动控制表.xlsx`、`table.xml`、`EPromotion.cs` 和 Service Attribute，理解配置到代码的映射。
8. 用日志或测试环境验证同一天重复进入、失败重试、支付取消、支付成功和重新登录补报。
