# 项目产出规范

## 唯一输出

每个项目只创建一个 Markdown：

```text
E:/实习产出/<项目名称>/<项目名称>-项目复盘.md
```

一级标题固定为：

```markdown
# <项目名称>｜项目复盘
```

## 文件命名规范

- 固定格式：`<项目名称>-项目复盘.md`。
- 项目名称使用清晰、稳定、能独立识别内容的中文简称。
- 允许中文、英文字母、数字和半角连字符 `-`。
- 禁止空格、日期、版本号、括号及 `最终版`、`新版`、`副本` 等后缀。
- 文件名建议控制在 10～30 个字符，避免完整需求句子。
- 更新同一项目时直接补充原文件，不创建第二份 Markdown。

示例：

```text
锦华活动埋点-项目复盘.md
支付订单补报系统-项目复盘.md
Unity资源热更新-项目复盘.md
```

不得创建 `README.md`、章节拆分文件、证据清单文件或其他辅助 Markdown。

## 内容要求

单个文档必须同时覆盖：

1. 项目概述、背景、目标和个人职责
2. 需求、约束和方案权衡
3. 架构与完整逻辑代码链条
4. 核心类、数据结构和代表性代码
5. 成功、失败、重试、去重和边界分支
6. 测试验证和实际效果
7. 风险、技术债和改进方案
8. 简历描述、STAR 讲述和面试追问
9. 重新学习清单
10. 证据来源与脱敏说明

## 篇幅控制

- 优先控制在 3,000～6,000 个中文字符。
- 复杂项目可以超过 6,000 字，但不得重复解释同一逻辑。
- 每段尽量不超过 5 行，每个列表优先控制在 3～7 项。
- 只保存能解释设计的代表性代码，不复制整文件。
- 复杂调用链优先使用 Mermaid、表格或分步流程代替长段落。
- 先保证完整逻辑链，再压缩背景、套话和重复总结。

## 事实等级

- **已验证**：来自源码、配置、日志、测试或版本差异。
- **合理推断**：根据调用关系得出，但没有运行证据。
- **未知**：当前环境无法确认。

禁止把推断写成事实，禁止编造业务指标。

## 完整性门槛

- [ ] 背景、目标、职责和范围清楚
- [ ] 入口到最终结果的逻辑链完整
- [ ] 核心类、字段、状态和参数清楚
- [ ] 网络、配置、异步、存储等适用链路已覆盖
- [ ] 成功、失败、重试和边界分支已覆盖
- [ ] 有足够的关键代码或伪代码
- [ ] 测试步骤、结果和证据清楚
- [ ] 工程效果与未验证业务效果分开
- [ ] 风险、限制和改进方向真实
- [ ] 简历和面试表达可由正文证据支撑
- [ ] 敏感信息已脱敏
- [ ] 不访问原仓库也能理解
- [ ] 项目目录中只生成一个 `<项目名称>-项目复盘.md`

任何适用项未满足时不得声称完成；无法确认的内容必须标为未知。
