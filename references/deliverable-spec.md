# 任务产出规范

## 目标

生成一套脱离项目源码、聊天记录和公司环境后仍然可以独立阅读的任务档案。读者应能回答：为什么做、怎么做、代码如何运行、哪里困难、如何验证、产生什么效果、面试时如何讲。

## 默认输出目录

在 `E:/实习产出/<任务名称>/` 创建以下固定文件名：

1. `00-任务总览.md`
2. `01-需求与问题分析.md`
3. `02-架构与完整逻辑链.md`
4. `03-关键代码与数据结构.md`
5. `04-测试验证与效果.md`
6. `05-风险复盘与改进.md`
7. `06-简历与面试材料.md`
8. `07-重新学习清单.md`
9. `08-证据清单.md`

## 文件命名规范

- 格式固定为：`两位序号-固定中文名称.md`。
- 序号从 `00` 连续到 `08`，不得跳号或重复。
- 文件名不得包含空格、日期、版本号、项目名或括号。
- 不得改成英文名、拼音名或临时名称，如 `README.md`、`summary.md`、`最终版.md`。
- 任务名称只放在父目录和文档一级标题中，不重复写入每个文件名。
- 更新已有任务时覆盖或补充同名文件，不创建 `新版`、`最终版2` 等副本。

任务较小时可以合并相邻文件，但不得省略完整逻辑链、关键代码、验证结果和面试材料。

## 事实等级

在重要结论旁明确区分：

- **已验证**：来自源码、配置、日志、测试或版本差异。
- **合理推断**：根据调用关系得出，但没有运行证据。
- **未知**：当前环境无法确认。

禁止把推断写成事实，禁止编造业务指标。

## 证据清单

记录产出依据，但不能仅列路径：

| 证据 | 当时位置/版本 | 提取出的关键信息 | 是否已写入自包含文档 | 脱敏说明 |
|---|---|---|---|---|

至少覆盖：

- 需求来源或任务描述
- 核心入口
- 主调用链
- 数据结构或协议
- 配置来源
- 测试或运行证据
- 版本差异或提交记录

未来路径可能失效，因此必须把关键结论和必要代码写入正文，而不是只保存链接。

## 完整性门槛

提交产出前逐项确认：

- [ ] 问题背景和用户/业务痛点清楚
- [ ] 范围内与范围外内容清楚
- [ ] 入口到最终结果的调用链完整
- [ ] 每个主要类和方法的职责清楚
- [ ] 核心字段、参数、返回值和状态清楚
- [ ] 网络、配置、持久化或异步链路已覆盖
- [ ] 成功、失败、重试、去重和边界分支已覆盖
- [ ] 有足够的关键代码或伪代码供未来理解
- [ ] 代码为什么这样设计解释清楚
- [ ] 测试步骤、预期结果和实际证据清楚
- [ ] 工程效果与业务效果分开
- [ ] 风险、限制和改进方向真实
- [ ] 简历描述能被正文证据支撑
- [ ] 面试追问有可验证回答
- [ ] 敏感信息已脱敏
- [ ] 不依赖原仓库也能理解

任何适用项未满足时不得声称完成。无法确认的项目必须写明原因和补充方式。

## 效果表达

优先使用可验证的工程结果：

- 覆盖了多少模块、路径或场景
- 减少了哪些重复代码或人工步骤
- 增加了哪些可靠性、可维护性或可观测性机制
- 修复了什么具体错误
- 测试通过了哪些场景

只有具备 BI、监控或对照实验时，才能写收入、转化率、性能提升百分比。
